# 测试用「长自我介绍」——粘贴到对话里触发画像/记忆提取

> 用法：把下面这段文字**整段复制**，作为一条消息发给 EchoMind。它的长度超过 1000 token，
> 会触发后台压缩任务（每 3 分钟跑一次）提取出正画像、负画像、语义/情节/程序记忆。
> 发完等 3 分钟，再运行 `python test/check_profile.py` 查看 `negative_profile` 是否被写入。

我叫林晚，之前在字节跳动做后端开发工程师，主要负责推荐系统的基础设施，用的是 Go 和 Python。今年年初我跳槽到了一家做跨境电商的公司，现在负责数据平台团队的架构设计，团队一共 12 个人。我自己最近在业余时间学习大模型应用开发，主要在看 LangChain 和 RAG 相关的东西，目标是年底能做出一个内部的知识库问答机器人，给运营团队用来查商品资料和历史营销活动。

我个人有几个明确的偏好，希望你能记住。第一，我喜欢简洁直白的回答，一句话能说清楚的就不要啰嗦，不要给我长篇大论。第二，回答里不要贴代码块，我真的不喜欢看代码，如果非要说明技术细节，请用文字描述。第三，不要叫我"老师"或者"林总"这种称呼，直接叫我名字就行。第四，不要用表格，用分点列出来就好。第五，涉及到数据的时候，请保留原始数字，不要四舍五入或者用"大约""左右"这种模糊的说法。

上个月我们团队做了一个商品数据清洗的项目，当时遇到了一个很麻烦的问题，就是商品标题里有大量乱码和重复的 sku 字段，导致下游的推荐系统老是出错。我花了三天时间写了一个清洗脚本，用正则表达式加规则匹配，最后把准确率从 82% 提到了 97%。这件事让我意识到，数据清洗的关键是先摸清楚脏数据的规律，再针对性写规则，而不是一上来就上复杂的模型。

我平时的工作流是：先跟业务方确认清楚需求边界，再拆解成小任务，每个任务先写一个最小可行的版本跑通，再逐步优化。我特别不喜欢那种一上来就讨论架构、画大饼的做法，先把能跑的版本做出来最重要。

对了，我下周三要跟老板汇报数据平台的季度规划，我需要准备一份汇报材料，重点讲清楚我们这一季度在数据质量和查询性能上做了哪些优化，以及下一季度准备引入哪些新工具。如果你能帮我梳理一下汇报的思路和重点，那就太好了。

我这个人比较在意时间，如果一个问题你觉得需要联网或者查资料才能准确回答，请直接告诉我，不要硬编。另外，如果我的问题不明确，你可以直接问我，而不是猜。
