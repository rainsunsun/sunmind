# sunmind 后端 · 消息流转与高并发

> 面试高频追问方向之一。本文分三块：**① 消息是怎么传入的**（现状已有、完整可讲）→ **② 高并发现状盘点**（做了哪些 / 缺哪些）→ **③ 补足方案**（问题 → 方案 → 面试话术）。

---

## 一、消息是怎么传入的（已有，完整可讲）

### 1.1 端到端链路

```
Streamlit 前端
  │  requests.get("/chat_with_agent/stream?query=..&knowledge_base_id=..&user_id=..&top_k=5", stream=True)
  ▼
FastAPI 路由 /chat_with_agent/stream
  │  StreamingResponse(stream_agent_response(...), media_type="text/plain")
  ▼
stream_agent_response()  —— 一个 async generator
  │  ① 新建 Redis 检查点 AsyncRedisSaver（多轮会话状态）
  │  ② get_or_create_agent()：拿全局 agent 单例（双检锁）
  │  ③ agent.astream(messages, config={thread_id=user_id},
  │       stream_mode=["messages","custom"], context=ContextSchema)
  │       ├─ "messages" 模式 → 逐 token 拿正文 → yield {"type":"answer","content":...}
  │       └─ "custom" 模式 → 工具调用状态 → yield {"type":"status","content":...}
  │  ④ 结束后 background_tasks.add_task(save_conversation_messages) 异步落库
  ▼
前端 r.iter_lines() 逐行 json.loads，按 type 渲染（status→工具状态条 / answer→打字机累加）
  ▼
（异步）save_conversation_messages → PG raw_conversations（human + ai 两条）
  ▼
（后台）每 3 分钟 check_and_store_memory → run_compression_task → 提取记忆 / 画像
```

### 1.2 每一步为什么这么做

| 环节 | 为什么 |
|---|---|
| StreamingResponse + async generator | ① 打字机体验；② 首 token 延迟低，不等完整答案生成完；③ 内存 O(1)，不把长答案整体缓存在内存 |
| stream_mode = ["messages","custom"] | messages 给正文、custom 给工具执行状态——否则 agent 调检索工具那 1~2 秒是"静默思考"，用户以为卡死 |
| 会话状态放 Redis（AsyncRedisSaver） | 多轮对话跨请求持久；thread_id=user_id；TTL 60min + refresh_on_read 保持活跃会话 |
| 落库用 BackgroundTasks | 不阻塞主链路：用户已收到流式回答，落库是"事后异步"，失败不影响本次回答 |
| 每行一条 JSON 而非整包 | 流式按行解析、边收边渲染，无需等完整报文 |

### 1.3 一句话面试话术

> "前端用 GET 流式请求打到 /chat_with_agent/stream，后端返回 StreamingResponse，底层是 agent.astream 的 async generator：messages 模式逐 token 出正文、custom 模式出工具状态，边生成边 yield 成 JSON lines 回前端；会话状态靠 Redis checkpoint 跨请求保持，消息落库用 BackgroundTasks 异步写、不阻塞主链路。"

## 二、高并发现状盘点

### 2.1 已经做了的（可讲"我有考虑并发"）

1. **连接池**：PG 用 asyncpg pool（min=10 / max=50）；Redis 单连接池 max_connections=20；全局单例复用，避免每请求建连。
2. **单例 + 双检锁**：PG / Milvus / Redis / agent 都是进程内单例，异步场景用 `asyncio.Lock` 双重检查，防止并发初始化出多个连接池。
3. **全局 agent 单例**：`create_agent` 编译好的图全局复用一次，避免每请求重建（编译有开销）。
4. **上传并发限制**：`asyncio.Semaphore(10)` 限制同时最多 10 个上传，防大文件上传打爆内存 / 连接。
5. **工具调用限流中间件**：`ToolCallLimitMiddleware` 限制 get_memory / search_knowledge_base 单轮各最多 1 次，防 agent 死循环拖垮服务。
6. **画像 Redis 缓存**：`user_profile:{id}` / `negative_profile:{id}`，TTL 1h，命中不查 PG。
7. **检索降级链**：混合检索失败 → 纯稠密；rerank 失败 → 按 RRF 顺序，保证外部依赖抖动时可用。

### 2.2 薄弱 / 缺失的（诚实讲 + 给方案）

1. **无 API 限流**：/chat 没有针对 user/ip 的 QPS 限制，高峰会直接打满外部 LLM API。
2. **无背压 / 并发闸门**：LLM 调用是秒级慢请求，无全局并发上限，突发流量会叠加放大。
3. **文档处理用进程内 BackgroundTasks**：非持久化任务队列——进程重启丢任务、无重试、无法横向扩 worker。
4. **每请求新建 Redis 检查点连接**：`stream_agent_response` 每次都 `AsyncRedisSaver.from_conn_string(...)` 新建再关闭，高 QPS 下建连开销被放大。
5. **外部 API 无统一熔断 / 超时 / 重试封装**：embedding / rerank / LLM 三类外部调用各自裸调。
6. **单进程运行**：`uvicorn.run` 未开 workers，单核单进程扛并发上限低。
7. **非标准 SSE**：media_type 是 `text/plain` + JSON lines，不是 `text/event-stream`。

## 三、补足方案（问题 → 方案 → 面试话术）

### 3.1 API 限流（rate limit）
- **方案**：慢路径 /chat 用 Redis 滑动窗口 / 令牌桶，per-user + per-ip 双层；快路径（列表类只读接口）轻量或跳过。用 FastAPI 依赖注入实现，超限返回 429 + `Retry-After`。
- **为什么**：外部 LLM 有 QPS 上限和计费，服务侧不拦，上游会被打爆或触发限流拖垮全站。
- **话术**："我做了双层限流：基于 Redis 滑动窗口按 user 和 ip 各限 QPS，命中返回 429；阈值按接口分——慢的 LLM 路径紧、只读列表松，避免单个用户把整个外部 API 额度打爆。"

### 3.2 背压 + 并发闸门
- **方案**：对 LLM / 检索这类慢请求加全局 `asyncio.Semaphore`（如 20~50），超出就排队等待，而不是无限并发；配合请求超时。
- **为什么**：asyncio 单线程协作式，慢请求 IO 等待不占 CPU，但并发数过高会撑爆连接池和外部 API。
- **话术**："我用信号量做背压——把同时在途的 LLM 调用数卡在上限，超出的排队，突发流量不会把上游 API 打崩，也保护本地连接池。"

### 3.3 文档处理 → 真正的任务队列
- **方案**：把"分块 + embedding + 入库"从 FastAPI BackgroundTasks 迁到 Celery + Redis broker（或 arq/dramatiq），任务持久化、失败重试、独立 worker 进程横向扩容。
- **为什么**：BackgroundTasks 跑在 web 进程里，会和请求抢 CPU/IO，进程重启任务就丢；向量化是 CPU + 外部 API 密集的重活，应和请求进程解耦。
- **话术**："文档处理是重任务，我从进程内 BackgroundTasks 迁到 Celery：上传接口只落临时文件 + 投递任务立刻返回，真正分块 / 向量化由独立 worker 异步做，任务可重试、可横向加 worker，避免大文件把 web 进程拖垮。"

### 3.4 连接复用（Redis 检查点）
- **方案**：把 AsyncRedisSaver 提升为全局单例 / 连接池复用，而不是每请求新建；或按 thread 做 LRU 缓存。
- **注意**：当前全局 agent 单例在**首次创建时**才绑定 checkpointer，与"每请求新建 checkpointer"的生命周期不匹配，是并发正确性隐患——面试被追问"单例 + 每请求建连怎么协调"要能讲清楚"agent 图无状态可共享，但 checkpointer 应复用、生命周期要和 agent 对齐"。
- **话术**："一开始每请求都新建 Redis 检查点连接，压测发现连接建立是热点，改成全局单例复用后 QPS 上去、延迟下来；同时把 checkpointer 的生命周期和 agent 单例对齐，避免跨请求用到已关闭的连接。"

### 3.5 外部 API 熔断 + 超时 + 重试
- **方案**：对 embedding / rerank / LLM 统一包一层客户端：显式 timeout（如 10s）、失败指数退避重试（1~3 次）、连续失败熔断降级。
- **为什么**：外部 API 偶发超时 / 限流不可避免，没有超时会把请求线程拖住；有熔断才能在依赖抖动时快速失败或降级。
- **话术**："所有外部调用统一走一个带 timeout + 重试 + 熔断的客户端封装；检索侧已有降级链，LLM 侧再补熔断，依赖抖动时不拖垮整体可用性。"

### 3.6 多进程 + 前置网关
- **方案**：uvicorn 开多 worker（或 Gunicorn 管理多 uvicorn worker），前面 Nginx 做负载均衡、静态缓存、连接保持。
- **注意点**：多 worker 下"进程内单例连接池"会变成"每进程一份"，需保证连接池 size 之和不超过 DB 上限。
- **话术**："单进程有 GIL 和单核瓶颈，用多 worker + Nginx 负载均衡横向扩展；同时注意每个 worker 各持一份连接池，总连接数要压测调好，别把 PG 连接上限打满。"

### 3.7 缓存补充
- **方案**：① query embedding 缓存（同一 query 向量复用）；② 检索结果短 TTL 缓存（热门 query）；③ 连接池参数压测调优。
- **为什么**：embedding 和 rerank 是外部 API，每次约 1s，缓存热门 / 重复 query 能省下大量外部调用。
- **话术**："embedding 是纯函数（同文本同向量），天然可缓存，我加了一层 TTL 缓存，重复或近似 query 直接复用，省掉外部 API 调用。"
