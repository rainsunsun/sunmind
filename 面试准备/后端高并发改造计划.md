# sunmind 后端高并发改造计划

> 对应《后端-消息流转与高并发.md》"补足方案"的落地版。目标：可执行——每条任务卡清现状、给改法、标优先级、定验收。既是工程路线图，也是面试被问"如果让你优化你怎么办"的答案素材。

---

## 0. 现状基线

- **部署**：单进程 `uvicorn.run(...)`，无 workers，无前置网关。
- **已有并发手段**：PG asyncpg 池（min=10 / max=50）、Redis `max_connections=20`、单例 + 双检锁、上传 `Semaphore(10)`、`ToolCallLimitMiddleware`、画像 Redis 缓存、检索降级链。
- **主要缺口**：无限流、无背压闸门、文档处理非持久化、每请求新建 Redis 检查点、外部 API 无熔断超时、单进程、非标准 SSE。

---

## 1. 路线图总览（按性价比排序）

| 阶段 | 任务 | 改动量 | 收益 | 风险 |
|---|---|---|---|---|
| P0 | ① Redis 检查点连接复用 | 小 | 高（每请求省建连） | 低 |
| P0 | ② 全局信号量背压 | 小 | 高（保护上游 + 连接池） | 低 |
| P0 | ③ 外部 API 超时 + 重试 + 熔断封装 | 中 | 高（可用性） | 低 |
| P1 | ④ API 限流（Redis 滑动窗口） | 中 | 高 | 低 |
| P1 | ⑤ 文档处理迁任务队列 | 大 | 高（解耦 + 持久化） | 中 |
| P2 | ⑥ 多 worker + Nginx | 部署层 | 高（吞吐） | 中 |
| P2 | ⑦ embedding / 检索缓存 | 中 | 中（省外部 API） | 低 |

## 2. 逐项任务卡

### P0-① Redis 检查点连接复用
- **现状问题**：`stream_agent_response` 每请求 `async with AsyncRedisSaver.from_conn_string(...)` 新建 + 关闭；且全局 agent 单例只在首次创建时绑定 checkpointer，与每请求新建的生命周期不匹配。
- **改法**：
  1. 模块级建一个复用的 AsyncRedisSaver 单例，`asetup()` 一次，应用退出时 `aclose()`；
  2. `get_or_create_agent` 首次用该单例 checkpointer，之后保持一致；
  3. checkpointer 本身按 `thread_id` 分区，复用是安全的，不会串会话。
- **涉及文件**：`backend/agent.py`、`backend/redis_cache.py`
- **风险**：复用后需在 lifespan 里正确关闭，否则进程退出连接泄漏。
- **验收**：同并发下建连耗时下降、无 "connection closed" 报错、多轮对话状态不串。

### P0-② 全局信号量背压
- **现状问题**：LLM / 检索是秒级慢请求，无并发上限，突发流量打爆外部 API 和本地连接池。
- **改法**：模块级 `_llm_semaphore = asyncio.Semaphore(30)`，在 `agent.astream` 前后 acquire/release；超限排队，配合请求超时（如 60s）返回 503。
- **涉及文件**：`backend/agent.py`（或独立 middleware）
- **风险**：阈值过高无效、过低排队积压；需压测定。
- **验收**：外部 API 429 率下降，本地 PG 池不耗尽。

### P0-③ 外部 API 超时 + 重试 + 熔断统一封装
- **现状问题**：embedding / rerank / LLM 三处外部调用裸调，无统一超时重试。
- **改法**：新建 `backend/external_client.py`，包一层：`asyncio.timeout`(10s)、指数退避重试(1~3 次，只对只读/幂等操作)、连续失败 N 次熔断（熔断期直接返回降级结果）。检索侧复用已有降级链，LLM 侧熔断后返回兜底文案。
- **涉及文件**：新建 `backend/external_client.py`；改 `backend/documents_process.py`(rerank)、`backend/milvus_client.py`(embedding)、`backend/agent.py`(LLM)
- **风险**：重试非幂等写操作会重复；只对只读重试。
- **验收**：人为断网 / 超时，服务返回降级结果而非卡死 / 抛 500。

### P1-④ API 限流
- **现状问题**：无 per-user / per-ip QPS 限制。
- **改法**：新建限流依赖 / 中间件，Redis 滑动窗口（`ZSET` 或 `INCR+EXPIRE`），双层 key `rl:user:{id}` / `rl:ip:{ip}`；慢路径 /chat 阈值紧（如 10/min/user），只读列表松或跳过；超限 429 + `Retry-After`。
- **涉及文件**：新建 `backend/rate_limit.py`；改 `backend/main.py`、`backend/api.py`
- **风险**：误伤正常高频用户；阈值可配 + 白名单。
- **验收**：脚本并发打超阈值即 429，正常流量不受影响。

### P1-⑤ 文档处理迁任务队列
- **现状问题**：分块 + embedding + 入库跑在 FastAPI BackgroundTasks 里，进程重启丢任务、无重试、和 web 进程抢资源。
- **改法**：上传接口改为"落临时文件 → 投递任务（含 file_hash/user_id/kb_id）→ 立即返回"；worker 消费做分块 / 向量化 / 入库。选型 Celery + Redis（成熟、生态全）或 arq（轻量、纯 asyncio）。
- **涉及文件**：`backend/documents_process.py`、`backend/api.py`、新增 worker 入口 + 任务定义
- **风险**：引入新组件；任务幂等靠 file_hash 去重（已有）；失败重试与告警。
- **验收**：上传大文件后 web 进程 CPU 稳定；kill 后重启 worker 能续跑。

### P2-⑥ 多 worker + Nginx
- **现状问题**：单进程单核。
- **改法**：uvicorn 多 worker 或 Gunicorn + uvicorn worker；前置 Nginx 做负载均衡、keep-alive、静态缓存。注意多 worker 下每进程一份连接池，总连接数压测调好。
- **涉及文件**：部署配置（docker-compose / systemd / nginx.conf）
- **风险**：单例连接池在多进程下各自持有一份；DB 连接上限。
- **验收**：压测吞吐线性提升，PG 不报 too many connections。

### P2-⑦ embedding / 检索缓存
- **现状问题**：embedding、rerank 每次外部调用约 1s，无缓存。
- **改法**：query embedding 缓存（文本→向量，纯函数，TTL 长）；检索结果短 TTL 缓存（热门 query）；用 Redis。
- **涉及文件**：`backend/milvus_client.py`、`backend/documents_process.py`
- **风险**：缓存与数据更新不一致，靠 TTL 兜底 + 上传时主动失效。
- **验收**：重复 query 的 embedding 外部调用降为 0，P99 延迟下降。

## 3. 压测与验证

- **工具**：Locust（可自定义流式请求）/ wrk / vegeta；外部 API 用 mock 限流。
- **场景**：① 只读列表接口高 QPS；② /chat 流式并发 50~200；③ 并发上传大文件。
- **指标**：P50 / P95 / P99 延迟、错误率(4xx/5xx)、外部 API 429 率、PG 池等待时长、Redis 连接数。
- **基线**：改造前后同一脚本对比，量化收益——这正是面试"你有数据吗"的底气。

---

## 4. 里程碑

- **M1（P0 完成）**：可用性兜底到位——外部依赖抖动不拖垮、连接复用、有背压。
- **M2（P1 完成）**：流量治理到位——有限流、文档处理解耦。
- **M3（P2 完成）**：吞吐扩展到位——多进程 + 网关 + 缓存，支撑真实并发。

---

## 5. 面试 1 分钟版（被问"你会怎么优化高并发"）

> "先做三件见效快的事：复用 Redis 检查点连接、给在途 LLM 调用加全局信号量背压、给所有外部 API 统一加超时 + 重试 + 熔断；再上 Redis 限流、把文档处理迁到任务队列解耦；最后多 worker + Nginx 横向扩展、补 embedding 缓存。每一步我都有压测指标量化收益，而不是嘴上说优化。"
