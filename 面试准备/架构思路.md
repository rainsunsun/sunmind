# EchoMind 架构思路（每个模块：做了什么 / 为什么 / 结果）

> 面试用：先说清"系统整体要解决什么问题"，再按模块讲"做了什么、为什么这么做、得到什么结果"。这套结构比背代码更能体现架构思维。

---

## 0. 系统要解决的三个问题

1. **检索不准**：单一向量检索对专有名词、编号、精确字段召回差。
2. **对话失忆**：普通 RAG 每次对话从零开始，无法个性化、无法连贯。
3. **多源一致性**：记忆/文档同时落在向量库 + 关系库 + 缓存，需要保证不丢不重。

围绕这三点，系统分成 **检索子系统**、**记忆子系统**、**Agent 编排**、**数据层** 四块。

---a

## 1. 应用入口与生命周期 — `main.py`

- **做了什么**：FastAPI 应用装配、lifespan 生命周期管理、启动后台记忆压缩任务、CORS/禁用缓存中间件。
- **为什么**：FastAPI 的 `@asynccontextmanager` lifespan 是唯一的"启动即初始化、退出即清理"钩子；把 PG/Milvus/Redis 三个客户端初始化放这里，保证请求进来时连接就绪；后台任务用 `asyncio.create_task` + 追踪集合，保证退出时能取消。
- **结果**：启动顺序清晰（PG → Milvus → Redis → 后台任务），任一初始化失败即启动失败，不会带着半残状态对外服务。

---

## 2. 路由层 — `api.py`

- **做了什么**：文档上传（流式接收 + 哈希去重 + 后台异步处理）、知识库 CRUD、文件删除、流式对话接口。
- **为什么**：上传用 **background_tasks** 把耗时的"解析→分块→向量化→双写"丢到后台，接口立即返回，避免大文件上传阻塞连接；文件哈希去重在入口拦截重复上传，省掉后续昂贵的 embedding。
- **结果**：上传体验快（秒回"处理中"），重复文件零成本跳过。

---

## 3. Agent 编排 — `agent.py`

- **做了什么**：用 LangChain `create_agent` 组装 Agent，配 3 个工具、4 类中间件，用 Redis 做 checkpoint 持久化会话；`stream_agent_response` 负责流式输出并异步落库对话。
- **为什么**：
  - 中间件把横切关注点（工具限流、动态提示词、自动摘要）从业务逻辑里抽出来，可插拔；
  - Redis checkpoint 让多轮对话状态跨请求存活（thread_id = user_id）。
- **结果**：Agent 行为可控（每个工具单轮最多调 1 次，防死循环）、提示词按知识库动态切换、对话自动摘要防上下文爆炸。

---

## 4. 工具集 — `tools.py`

- **做了什么**：`search_knowledge_base`（知识库混合检索）、`get_memory`（四类记忆并行检索）、`get_raw_conversation_by_summary_id`（按摘要 id 回查原始对话）。
- **为什么**：把"检索"封装成工具让 LLM 自主决定**何时调、调哪个、并行调**，比硬编码流程更灵活；`get_memory` 让模型自己决定每类记忆召回几个（k 值），避免无脑全量召回。
- **结果**：事实问题走知识库、偏好问题走记忆、混合问题两路并行，工具调用不空转。

---

## 5. 提示词配置中心 — `config.py`

- **做了什么**：把 BASE_PROMPT、默认/指定知识库两套系统提示词、记忆提取提示词、正/负画像合并提示词全部集中管理。
- **为什么**：提示词是 LLM 应用的"代码"，集中管理方便迭代和版本对比；把画像放在提示词**末尾**是为了命中 LLM prompt 缓存（前缀稳定，缓存从头部连续命中，省 token）。
- **结果**：改提示词不动业务代码；回答风格、工具调用规则、负画像硬约束都在一处收敛。

---

## 6. 文档处理管道 — `documents_process.py`

- **做了什么**：PDF/Word 解析 → **父子块分块** → 双写（子块→Milvus，父块→PG）→ rerank 重排序。
- **为什么**：分块是 RAG 质量的第一道关卡。小块召回准但上下文破碎，大块上下文全但召回信号被稀释；**父子块**把两者解耦——用小子块做检索，命中后回取大父块喂给 LLM。
- **结果**：检索精度（小粒度）与生成质量（大上下文）兼得。

---

## 7. 知识库检索 — `knowledge_base_manager.py`

- **做了什么**：集合初始化（BM25 内置函数）、`add_chunks_batch`、`hybrid_retrieval_knowledge_base` 混合检索。
- **为什么**：稠密向量擅长语义相近、稀疏 BM25 擅长精确词/编号，两者互补；`AnnSearchRequest` 双路 + `RRFRanker` 融合，失败自动降级为纯稠密检索兜底。
- **结果**：召回从"单一路径"升级为"双路互补 + 降级兜底"，可用性与命中率都提升。

---

## 8. 记忆检索 — `memory_manager.py`

- **做了什么**：四类记忆并行混合检索 → 综合评分排序（语义 45% + 时近性 25% + 重要性 30%，类型加权）→ 更新 last_access_at → 相似度 ≥0.9 去重。
- **为什么**：记忆不仅要"相关"还要"新鲜"和"重要"，单看向量相似度会召回过期或无关的记忆；时间衰减（每小时 0.5%）让最近用过的记忆权重更高。
- **结果**：记忆召回更贴合当下语境，且通过去重控制记忆库规模。

---

## 9. Milvus 门面 — `milvus_client.py`

- **做了什么**：单例封装 `AsyncMilvusClient`，统一初始化知识库/记忆两个集合，把记忆管理和知识库管理的方法代理出去。
- **为什么**：集合 schema、索引、BM25 函数等初始化逻辑集中在一处，业务方拿到的就是一个"能用的客户端"；单例避免重复建连接。
- **结果**：上层（tools/agent）不感知集合细节，代码分层清晰。

---

## 10. PostgreSQL 数据层 — `postgresql_client.py`

- **做了什么**：6 张表（users / knowledge_bases / file_metadata / parent_chunks / chunk_hashes / raw_conversations）+ 6 个索引；连接池；画像读写带 Redis 缓存。
- **为什么**：关系库负责"精确检索 + 事务 + 级联删除"（父块按 id 取、画像更新、对话记录、去重哈希），向量库负责"语义检索"，各司其职；外键 ON DELETE CASCADE 让删除知识库/文件自动清理关联数据。
- **结果**：结构化数据强一致，删除操作不用手动清理多表。

---

## 11. Redis 缓存 — `redis_cache.py`

- **做了什么**：用户画像/负画像缓存（TTL 1 小时）+ 会话 checkpoint 存储。
- **为什么**：画像每次对话都要读（注入提示词），走 DB 太频繁，缓存命中直接返回；checkpoint 需要低延迟读写以支撑多轮对话状态。
- **结果**：画像读路径命中缓存时零 DB 开销，会话状态跨请求持久。

---

## 12. 记忆后台闭环（DPU）— `auto_store_memory_from_psql.py`

- **做了什么**：每 3 分钟扫描未压缩对话 → token 超阈值(1000)触发 LLM 提取 → 新旧画像合并 → 双写 PG/Milvus → 注入提示词 → 失败回滚。
- **为什么**：这是"记忆"能**动态更新**的核心闭环。提取、合并、持久化、注入四步缺一不可；负画像合并用"只增不减"策略，正画像合并用"冲突以新为准"策略。
- **结果**：用户画像随对话持续演进，且任一步失败不会产生半提交数据。

---

## 13. 去重存储 — `hash_storage.py`

- **做了什么**：文件级（SHA-256 整文件）与块级（SHA-256 子块内容）双重去重。
- **为什么**：文件级去重避免重复上传；块级去重避免不同文件里的相同段落重复 embedding、重复占用向量存储。
- **结果**：存储成本与计算成本双减。

---

## 14. 前端 — `frontend/app.py + style.css`

- **做了什么**：Streamlit 界面，SSE 流式接收、乐观 UI 更新、骨架屏、知识库管理、消息气泡。
- **为什么**：Streamlit 开发快、适合演示；乐观更新（先更新界面、后台异步确认）让交互不卡顿。
- **结果**：可视化演示完整可用，能直接展示"个性化 + 知识库 + 记忆"三大能力。

---

## 一句话总结（面试收尾）

> "这是一套**检索增强 + 长期记忆**的个性化问答系统：检索上靠父子块 + 混合检索 + 重排序 + 降级兜底保证准；记忆上靠后台 DPU 闭环把对话变成可持续更新的四类记忆和正/负画像；数据上靠 PG/Milvus/Redis 分层 + 回滚保证一致。"
