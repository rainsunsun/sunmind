# EchoMind 各模块具体设计（面试深挖版）

> 这里给出的是"被追问到实现细节时能画出来的东西"：表结构、算法参数、关键流程。

---

## 1. 父子块分块设计

```
参数（config.py）：
  parent_chunk_size=1000, parent_chunk_overlap=200
  child_chunk_size =200,  child_chunk_overlap =50
  separators = ["\n\n", "\n", "。", "！", "？", "，", "、", " ", ""]
```

- **拆分方式**：`RecursiveCharacterTextSplitter` 按中文标点/换行优先级递归切分，先生成父块，再在每个父块内切子块。
- **存储位置**：
  - 子块 → Milvus（带 `parent_id`、`knowledge_base_id`、`user_id`、`file_hash` 元数据，dense_vector + BM25 稀疏向量）
  - 父块 → PostgreSQL `parent_chunks`（`parent_id` 主键，`text` 全文）
- **检索时**：子块混合检索命中 → 取 `parent_id` 去重 → 回 PG 取父块全文 → 喂给 rerank/LLM。
- **为什么重叠 200/50**：防止关键信息恰好落在切分边界被截断。

## 2. 混合检索 + RRF 设计

```
dense_req:  HNSW + COSINE, ef=64, limit = top_k*7
sparse_req: BM25,             limit = top_k*3
hybrid_search(reqs=[dense_req, sparse_req], ranker=RRFRanker(), limit=top_k*3)
```

- **稠密路**：query 经 embedding 成 1024 维向量，HNSW 图搜索 + COSINE 度量，负责语义相近。
- **稀疏路**：Milvus `Function(FunctionType.BM25)` 对 `text` 字段内置生成稀疏向量，负责精确词/编号/专有名词。
- **RRF 融合**：`score(d) = Σ_r 1/(k + rank_r(d))`，只关心排名、忽略分数量纲，天然适合稠密/稀疏分数不可比的情况。
- **降级策略**：
  1. 混合检索异常 → 降级纯稠密检索（HNSW + COSINE）。
  2. rerank 失败 → 降级为 RRF 融合后的原始顺序截取 top_k。

---

## 3. Rerank 重排序设计

- **流程**：召回 N 个父块 → 调重排序模型（`bge-reranker-v2-m3` 等）对 query + 每个父块打分 → 取 `relevance_score` 最高的 top_k 作为最终上下文。
- **为什么**：召回阶段的向量/BM25 分是"粗排"，rerank 用更强的交叉编码器做"精排"，显著提升最终喂给 LLM 的片段相关性。
- **容错**：rerank 接口异常时，直接返回召回顺序的前 top_k，保证链路不断。

## 4. 记忆 Schema（Milvus memory_collection）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | VARCHAR(50) | 主键，auto_id |
| user_id | INT64 | **partition key**（多租户隔离） |
| thread_id | VARCHAR(100) | 会话 id |
| memory_type | VARCHAR(30) | summary / semantic / episodic / procedural |
| content | VARCHAR(65535) | 记忆正文（启用中文分词 + BM25） |
| summary_id | VARCHAR(50) | 关联摘要，非摘要记忆为 NULL |
| importance | FLOAT | LLM 提取时的重要性分 |
| created_at / last_access_at | INT64 | 创建/最近访问时间戳 |
| vector | FLOAT_VECTOR(1024) | HNSW + COSINE |
| sparse_vector | SPARSE_FLOAT_VECTOR | BM25 内置生成 |

- **四种记忆**：摘要（summary，对话浓缩）、语义（semantic，稳定事实/偏好）、情节（episodic，具体事件，`YYYY-MM-DD:` 开头）、程序（procedural，可复用工作流）。
- **多租户**：`user_id` 设为 partition key，集合 `partitionkey.isolation=True`，所有查询都带 `user_id` 过滤表达式，物理隔离。

## 5. 记忆排序算法（get_the_top_k_memories）

```
final_score = (alpha*semantic + beta*recency + gamma*importance) * type_weight

alpha = 0.45   # 语义相似度（向量分）
beta  = 0.25   # 时近性：recency = DECAY_RATE^hours_passed, DECAY_RATE=0.995（每小时衰减0.5%）
gamma = 0.30   # 重要性（LLM 评分）

type_weight: summary=0.7, semantic=1.3, episodic=1.0, procedural=1.2
```

- 命中后回写 `last_access_at`（partial_update），让下次检索"越常被用越靠前"。

---

## 6. 记忆去重设计（resolve_conflicts）

- 新提取的记忆与库里同类型记忆做**向量相似度**比较，`distance >= 0.9` 判定为重复 → 丢弃新记忆（摘要则置空）。
- 分类型并行检索比较（semantic/episodic/procedural/summary），`asyncio.gather` 并行。

## 7. 用户画像设计（正画像 + 负画像）

- **正画像 user_profile**：一段文字，身份/背景/偏好/目标（局部、可演进）。
- **负画像 negative_profile**：一段文字，禁忌/反感/明确拒绝（全局硬约束）。
- **存储**：PG `users` 表两列 + Redis 缓存（`user_profile:{id}` / `negative_profile:{id}`，TTL 3600）。
- **合并策略**：
  - 正画像 `USER_PROFILE_MERGE_PROMPT`：冲突以新增为准，但不冲突的旧信息保留。
  - 负画像 `NEGATIVE_PROFILE_MERGE_PROMPT`：**宁可多留不可误删，只增不减**。
- **注入**：system prompt 里负画像放在正画像**之前**（`【用户负画像·绝对禁止违反】` 排在 `用户画像：` 前），且 BASE_PROMPT 声明"负画像是最高优先级硬约束"；画像整体放在 prompt 末尾以命中缓存。

## 8. DPU 记忆闭环（动态画像更新）

```
每 180s 后台任务
  → 扫 raw_conversations 中 summary_id IS NULL 的消息
  → token 数 > TOKEN_THRESHOLD(1000) 才触发
  → LLM 提取 7 字段（summary/semantic/episodic/procedural/user_profile/negative_profile/filtered_message_ids）
  → resolve_conflicts 去重
  → 正/负画像分别 merge（LLM）
  → 写 PG：summary_id 标记 + user_profile + negative_profile
  → 写 Milvus：add_memories_batch
  → 任一步失败：回滚（summary_id 置空、画像还原旧值）
```

- **为什么 1000 阈值 + 中间件 10000 阈值分开**：后台压缩阈值（1000）控制"多久生成一次长期记忆"，SummarizationMiddleware 的 10000 阈值控制"单次上下文窗口内多久做摘要"，两者目的不同。

## 9. Agent 中间件设计

```python
middleware = [
  ToolCallLimitMiddleware("get_memory", run_limit=1),          # 单轮最多检索1次记忆
  ToolCallLimitMiddleware("search_knowledge_base", run_limit=1),# 单轮最多检索1次知识库
  dynamic_prompt,                                               # 按知识库切换系统提示词
  SummarizationMiddleware(trigger=("tokens",10000), keep=("messages",20)),
]
```

- **dynamic_prompt**：读 `knowledge_base_id` 决定用默认库（可发散）还是指定库（零发散，严格只答库内）提示词；同时读 user_id 注入正/负画像。
- **限流中间件**：防止 agent 无限循环调用工具。

## 10. PostgreSQL 表结构（6 表 + 索引）

| 表 | 用途 | 关键设计 |
|----|------|----------|
| users | 用户 + 正/负画像 | `user_id` 主键，画像两列 |
| knowledge_bases | 知识库归属 | 复合主键 `(kb_id, user_id)`，级联删除 |
| file_metadata | 文件元数据 | 复合主键 `(file_hash, kb_id, user_id)`，级联删除 |
| parent_chunks | 父块全文 | `(parent_id, kb_id, user_id)`，级联删除 |
| chunk_hashes | 子块去重哈希 | `(chunk_hash, file_hash, kb_id, user_id)` |
| raw_conversations | 原始对话 | `summary_id` 标记是否已压缩 |

- **级联删除**：删知识库/文件时，外键 `ON DELETE CASCADE` 自动清关联表，避免脏数据。
- **索引**：`idx_user_created`/`idx_thread_created`/`idx_summary_id`（对话）、`idx_chunk_hash`（去重查）、复合索引加速文件/父块查询。

---

## 11. 对话数据流

```
用户输入 → FastAPI(/chat_with_agent/stream)
  → Agent(工具调用：search_knowledge_base / get_memory / 可选并行)
  → 动态提示词注入画像 → LLM 流式生成 → 逐 token 返回
  → 异步落库 raw_conversations(human/ai)
  → (后台 3 分钟) 提取记忆 → 画像更新 → 注入下轮对话
```

## 12. 关键设计取舍速查（面试快答）

| 问题 | 答案要点 |
|------|----------|
| 父块为何放 PG | 只需按 id 精确取回，无需向量检索；事务/级联删除更省心；省向量存储 |
| 为何 RRF 不用加权融合 | 稠密/稀疏分数量纲不同，RRF 只看排名更鲁棒 |
| 为何画像放 prompt 末尾 | 前缀稳定命中 LLM 缓存，省 token |
| 为何负画像独立 | 禁忌是硬约束，需最高优先级且只增不减，与偏好混在一起会被模型弱化 |
| 为何 user_id 做 partition key | 物理隔离多租户，检索天然带过滤，避免跨用户数据串 |
| 为何 1000/10000 两个阈值 | 分别控制"长期记忆生成频率"与"上下文窗口内摘要" |
