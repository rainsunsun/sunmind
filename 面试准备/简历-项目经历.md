## 一、项目定位（一句话）

基于 RAG + 长期记忆的**个性化 AI 问答系统**：让 AI 在每次对话中"记得"用户是谁、偏好什么、反感什么，并结合私有知识库做高精度检索回答。

- 时间：2025 年（持续迭代）
- 技术栈：Python / FastAPI / LangChain + LangGraph / Milvus（Zilliz Cloud）/ PostgreSQL / Redis / Streamlit / DeepSeek + SiliconFlow（embedding & rerank）

## 二、项目经历（可直接粘贴进简历）

**EchoMind —— 个性化 AI 问答助手**（个人项目 / 独立开发）

- 设计并实现 **RAG 检索链路**：采用「父子块」分块策略（父块 1000 字符存 PostgreSQL、子块 200 字符存 Milvus），稠密向量（HNSW + COSINE）与 BM25 稀疏检索经 **RRF 融合**，再由重排序模型二次排序；子块保证召回精度、父块保证上下文完整，兼顾语义检索与关键词精确匹配。
- 构建 **长期记忆系统**：后台任务每 3 分钟扫描未压缩对话，超 token 阈值后由 LLM 自动提取摘要/语义/情节/程序四类记忆 + 用户画像；画像采用「**全局负画像 + 局部正画像**」双画像设计，负画像（用户禁忌）作为最高优先级硬约束注入 system prompt，实现可动态更新的个性化回答。
- 记忆检索实现 **多维度排序算法**：综合语义相似度（45%）+ 时近性（25%，带时间衰减）+ 重要性（30%）并按记忆类型加权，同时基于向量相似度 ≥0.9 自动去重，避免记忆库膨胀。
- 基于 **LangGraph / LangChain create_agent** 构建 Agent：3 个工具（知识库检索 / 记忆检索 / 原始对话回溯）+ 动态提示词中间件 + 工具调用限流中间件 + 摘要中间件，支持流式输出与工具调用过程可视化。
- 保证 **跨异构存储的数据一致性**：记忆写入横跨 PostgreSQL 与 Milvus，实现「任一存储失败则全量回滚」的补偿事务机制；文档侧设计 SHA-256 文件级 + 块级双重去重。
- 分层存储设计：PostgreSQL（父块/对话/画像/元数据）+ Milvus（向量）+ Redis（画像缓存 + 会话 checkpoint），画像缓存命中直接返回，降低数据库压力。

## 三、面试自述（1 分钟版本）

"我做了一个个性化 RAG 问答系统 EchoMind。它解决的是普通 RAG 的两个痛点：一是检索只靠单一向量、关键词和专有名词容易召回不准；二是每次对话 AI 都是'失忆'的。我的做法是：检索上用父子块 + 混合检索（稠密向量 + BM25）经 RRF 融合再加重排序；记忆上用后台任务自动把历史对话提取成四类记忆和用户画像，画像拆成'正画像（偏好）'和'负画像（禁忌）'，负画像作为硬约束每次注入提示词，保证动态更新、只增不减。技术栈是 FastAPI + LangGraph + Milvus + PostgreSQL + Redis。这里面我觉得最有意思的是记忆闭环的数据一致性——跨 PG 和 Milvus 两个异构存储，我做了失败回滚。"

## 四、STAR 故事线（面试追问素材）

**1. 为什么要把画像拆成正/负画像？**（设计权衡）
- 情境：画像只存一段话时，用户的"禁忌"（不要贴代码、不要叫我老师）和"偏好"（喜欢简洁）混在一起，模型可能只遵守一部分。
- 任务：让禁忌成为真正不可违反的约束，且随对话动态更新。
- 行动：把画像拆成 negative_profile（全局硬约束，注入时放最前面、规则声明"任何情况不得违反"）和 user_profile（局部偏好）；负画像合并用专门 prompt 做到"宁可多留不可误删、只增不减"。
- 结果：禁忌基本不再被违反，且画像可持续演进不丢失旧信息。

**2. 跨 PG + Milvus 的一致性怎么保证？**
- 情境：一条记忆既要写 Milvus（向量）又要写 PG（画像 + 给原始对话打 summary_id 标记）。
- 行动：先写 PG 的 summary_id 标记和画像（每步失败即回滚），最后写 Milvus；Milvus 失败则把 PG 已写的全部回滚（summary_id 置空、画像还原旧值）。
- 结果：不会出现"标记已压缩但向量没存进去导致记忆丢失"的半提交状态。

**3. 检索召回不准怎么办？**
- 行动：单路向量 → 加 BM25 关键词路 → RRF 融合 → 重排序二次精排；再加两层降级（混合检索失败退化为稠密检索，rerank 失败退化为 RRF 顺序）。
- 结果：专有名词/编号类 query 召回显著变好，服务可用性有兜底。

## 五、可被追问的"坑"（提前准备）

- 为什么父块存 PG 不存 Milvus？（父块只需按 id 精确取回，不需要向量检索，放关系库更省向量存储成本且事务/级联删除好做）
- 为什么画像放在提示词最后？（prompt 前缀稳定 → 命中 LLM 缓存，省 token；画像放前面会因画像变化导致整段缓存失效）
- RRF 和加权分数融合的区别？（RRF 只关心排名不关心分数量纲，稠密/稀疏分数不可比时更鲁棒）
