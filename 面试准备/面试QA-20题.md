# EchoMind 面试 QA 20 题（贴合大厂 RAG/AI 应用面试）

> 深挖追问见 [[面试-项目拷打篇]]；高并发落地见 [[后端高并发改造计划]]；消息流转 / 高并发现状见 [[后端-消息流转与高并发]]。

> 每题给"考官在问什么 + 参考答案"。回答套路：先一句话结论，再展开原理，最后补一个 trade-off 或坑。

---

**Q1. 介绍一下这个项目的整体架构？**
- 考官想听：能不能用一句话定位 + 分层讲清楚。
- 答：这是一套"检索增强 + 长期记忆"的个性化问答系统。分四层：**接入层**（FastAPI + Streamlit）、**Agent 编排层**（LangGraph agent + 中间件 + 工具）、**检索/记忆层**（父子块 + 混合检索 + 重排序；四类记忆 + 正/负画像 + DPU 闭环）、**数据层**（Milvus 存向量、PostgreSQL 存结构化、Redis 存缓存和会话 checkpoint）。核心卖点是"记忆可动态更新"和"检索有降级兜底"。

**Q2. 为什么用父子块（parent-child chunking）？**
- 答：分块大小是精度和上下文的矛盾。小块召回准但信息碎片化，大块上下文全但向量被稀释、召回不准。父子块把两者解耦：用小子块（200 字符）做向量检索保证命中率，命中后通过 `parent_id` 回取大父块（1000 字符）喂给 LLM 保证上下文完整。代价是多一次 PG 回查和额外存储父块。

**Q3. 混合检索是什么？稠密和稀疏怎么融合？**
- 答：稠密向量检索（embedding + HNSW/COSINE）擅长语义相近但口语/同义改写，稀疏检索（BM25）擅长精确词、编号、专有名词，两者互补。融合用 **RRF（倒数排名融合）**：`score = Σ 1/(k + rank)`，对两路各自排序后按排名融合取 top-k。

**Q4. 为什么用 RRF 而不是直接加权分数？**
- 答：稠密相似度（0~1 的 COSINE）和 BM25 分数（无上限）量纲完全不同，直接加权需要归一化、对超参敏感。RRF 只关心"排名"不关心"分数绝对值"，天然鲁棒、无需调权。代价是丢失了分数大小信息，但对融合排序场景通常更稳。

**Q5. 为什么要做 rerank 重排序？**
- 答：召回是"粗排"，双塔/向量分只保证相关片段在候选集里，不保证顺序最优；rerank 用交叉编码器（query + document 拼接打分）做"精排"，相关性判断更准。召回 top-N 后用 rerank 精排再取 top-k，能显著提升最终答案质量。代价是 rerank 是按对计算、更慢更贵，所以只对少量候选做。

**Q6. HNSW 是什么？为什么选 COSINE 度量？**
- 答：HNSW 是分层的可导航小世界图，查询时从高层粗粒度图逐步下降到低层做局部搜索，复杂度近似 O(logN)，用 M（每层邻居数）、efConstruction/ef 权衡建索引成本与召回精度。文本向量用 COSINE 是因为向量模长不影响语义方向，且归一化后余弦等价内积；L2 对文本 embedding 不如余弦稳定。

**Q7. BM25 在 Milvus 里怎么实现的？**
- 答：Milvus 提供内置 `Function(FunctionType.BM25)`，声明输入字段（text）→ 自动生成稀疏向量字段（sparse_vector），无需自己实现分词和倒排。稀疏向量建 `SPARSE_INVERTED_INDEX`，混合检索时作为一路 `AnnSearchRequest` 参与 RRF。分词用中文 analyzer（`analyzer_params={"type":"chinese"}`）。

**Q8. 检索的降级策略怎么设计的？**
- 答：两层降级。第一层：混合检索失败 → 降级为纯稠密向量检索；第二层：rerank 失败 → 降级为 RRF 融合的原始顺序截取 top_k。目的：外部依赖（embedding/rerank API、Milvus）偶发失败时服务不断、仍有可用结果，保证可用性优先于精度。

**Q9. 长期记忆系统怎么做的？四种记忆是什么？**
- 答：后台任务每 3 分钟扫未压缩对话，超 token 阈值后由 LLM 一次性提取：**摘要**（对话浓缩）、**语义**（稳定事实/偏好）、**情节**（具体事件，带日期）、**程序**（可复用工作流）+ 用户画像。记忆存 Milvus（可向量检索），原始对话存 PG 并用 summary_id 标记已压缩。这样既保留了细节又避免上下文无限膨胀。

**Q10. 用户画像怎么动态更新？（DPU 闭环）**
- 答：画像不是静态配置，是"提取→合并→持久化→注入"的闭环：每轮后台压缩时 LLM 会顺带提取新画像片段 → 用专门 merge prompt 与旧画像融合（正画像"冲突以新为准但保留旧信息"，负画像"只增不减"）→ 写 PG + Redis → 下一轮对话通过 dynamic_prompt 注入 system prompt。任一步失败回滚，保证不产生半更新。

**Q11. 正画像和负画像为什么要分开？**
- 答：两类信息约束强度不同。负画像（禁忌，如"不要贴代码""别叫我老师"）是**硬约束**，必须最高优先级、任何情况不可违反；正画像（偏好）是**软约束**，只影响风格。混在一段话里模型容易只遵守一部分。分开后负画像单独注入、单独合并（只增不减防止禁忌被"洗掉"），正画像自由演进。

**Q12. 记忆怎么去重？为什么用向量相似度？**
- 答：新提取记忆与库中同类型记忆算向量相似度，≥0.9 判重丢弃（摘要则置空）。用向量相似度是因为两段文字可能措辞不同但语义相同，精确字符串比对会漏；而向量能捕获语义等价。按类型分组并行比较，避免跨类型误删。

**Q13. 记忆检索的排序算法？**
- 答：`final = (0.45*语义相似度 + 0.25*时近性 + 0.30*重要性) * 类型权重`。时近性用指数衰减 `0.995^hours`（每小时衰减 0.5%），重要性来自 LLM 提取时的打分，类型权重语义 1.3/程序 1.2/情节 1.0/摘要 0.7。三个维度分别覆盖"相关、新鲜、重要"，比单看相似度更贴合人脑回忆。

**Q14. 记忆和知识库为什么分开存？检索有何区别？**
- 答：两者语义不同：知识库是"客观权威事实"，记忆是"关于这个用户的主观历史"。分开存一是隔离数据（记忆带 user_id 强隔离，知识库按知识库 id），二是提示词里明确"事实问题走知识库、偏好问题走记忆、混合问题并行"，避免用个人偏好污染事实回答、或漏掉个性化。区别在于记忆检索多了时近性/重要性评分和去重，知识库检索多了 rerank 精排。

**Q15. LangGraph/LangChain agent 怎么做工具调用？**
- 答：用 `create_agent` 声明模型 + 工具列表 + context_schema，agent 内部是"模型决定调用哪个工具 → 执行 → 把结果喂回模型 → 继续或作答"的循环。我用中间件做横切控制：`ToolCallLimitMiddleware` 限制每个工具单轮调用次数防死循环，`SummarizationMiddleware` 在 token 超限时自动摘要老对话，`dynamic_prompt` 动态切换提示词。

**Q16. 动态提示词中间件做什么？为什么画像放最后？**
- 答：`dynamic_prompt` 在每次模型调用前根据 `knowledge_base_id` 选择默认库（可发散）或指定库（零发散、严格只答库内）两套提示词，并把正/负画像注入。画像放 prompt **末尾**是为了命中 LLM 的 prompt 缓存——缓存从头连续匹配，画像在头部会因每次变化导致整段缓存失效；放末尾则前面稳定部分照常命中，省 token 省成本。

**Q17. 跨 PG + Milvus 的一致性怎么保证？**
- 答：记忆写入涉及两个异构存储，没有跨库事务，所以做**补偿式回滚**：先写 PG 的 summary_id 标记和画像（每步失败即回滚），最后写 Milvus；一旦 Milvus 失败，把 PG 已写的 summary_id 置空、画像还原旧值。保证不会出现"标记已压缩但向量没存进去"导致记忆永久丢失的半提交状态。这是分布式一致性里"最终一致 + 失败补偿"的思路。

**Q18. Redis 在这项目里做什么用？**
- 答：两个用途。一是**画像缓存**：`user_profile:{id}`/`negative_profile:{id}`，TTL 1 小时，每次对话注入提示词都要读画像，缓存命中避免频繁查 PG。二是**会话 checkpoint**：LangGraph 用 `AsyncRedisSaver` 存对话状态，让多轮对话跨请求持久（thread_id=user_id），TTL 60 分钟、读取刷新。

**Q19. 为什么父块放 PG 不放 Milvus？**
- 答：父块只需要按 parent_id 精确取回，不做向量检索，放关系库更合适：省向量存储成本（父块量大）、天然支持事务和 `ON DELETE CASCADE` 级联删除、按 id 精确查询比向量库简单。向量库只存真正需要语义检索的子块和记忆。

**Q20. 多用户数据隔离怎么做的？**
- 答：两层。存储层：Milvus 集合把 `user_id` 设为 **partition key** 并 `partitionkey.isolation=True`，物理隔离 + 查询自动分区裁剪；PG 所有表都以 `user_id` 参与主键/过滤。查询层：所有检索的过滤表达式都强制带 `user_id == xxx`（指定知识库再加 `knowledge_base_id == xxx`），从根上杜绝跨用户数据串。当前 thread_id 直接用 user_id，尚未做会话级隔离，这是可改进点。

### 加分追问（如果还有时间）

- **Q. 查询改写为什么要在 prompt 里强制？** 用户口语/模糊 query 直接检索效果差，让 LLM 先改写成"去口语化、保留术语、标准陈述式"的检索词再调 `search_knowledge_base`，提升召回。
- **Q. 流式输出怎么实现的？** 后端 `StreamingResponse` + agent `astream` 逐 token yield（`stream_mode=["messages","custom"]`），前端 `requests.iter_lines` 逐行解析 JSON，边收边渲染出打字机效果。
- **Q. 当前最大的性能瓶颈和优化方向？** 每次请求多库往返（PG/Redis/Milvus + 外部 embedding/rerank API），embedding 约 1s、rerank 约 1s；优化方向：Redis 连接池（当前每请求建连）、缓存 embedding、并行检索（已做）、画像缓存（已做）。
